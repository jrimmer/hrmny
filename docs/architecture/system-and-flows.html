Cytale · System Architecture

One BEAM, one wire, five shared packages

Cytale is a team-chat app in the Discord lineage: an Elixir/OTP server (Phoenix backend-only, raw WebSock gateway — deliberately not Phoenix Channels), ScyllaDB for truth, Tantivy (Rust NIF) for search, and a React SPA that consumes a shared TypeScript core (protocol · api-client · gateway-client · state · domain) intended to be reused verbatim by the future React-Native and bot clients. REST is the write path; the gateway is the fan-out path.

01 Runtime topology

Every client speaks the same two planes: REST for writes and reads, a raw WebSocket for real-time dispatches. A connection is one BEAM process (GatewaySocket, a WebSock handler); a workspace is one GenServer under a DynamicSupervisor. No Phoenix Channels, no PubSub — fan-out is per-PID through an ETS route table.

02 Login & session restore

Two token classes with different homes: the access JWT (15 min, in memory + mirrored to localStorage as last-seen because the refresh contract needs its sub) and the rotating refresh token (30 days, localStorage). Gateway Identify presents a live JWT — the token provider rotates it before identifying if expired.

03 Message posting & fan-out

Optimistic send on the client; idempotent insert on the server; at-least-once delivery on the wire with per-session sequencing. The same path serves thread replies with a second, thread-scoped dispatch.

Claim: the REST response confirms the optimistic row (nonce replaced by the server snowflake), while every other subscriber receives the same message as a seq-stamped dispatch — buffered before the wire write, so a subscriber that drops mid-flight resumes from the exact sequence it processed. Edits and deletes ride the same seam (MessageUpdate, MessageDelete with thread_id).

04 Presence management

Presence is derived, not stored: the route table answers “connected”, the preferred-status table answers “broadcasting what”. Invisible is display-honest — the wire says offline to everyone while routing stays fully live.

Claim: order-independence — whoever connects, every roster converges: the newcomer gets a backfill snapshot of who was already live, and existing members get the announce. Client-declared offline is rejected; offline is server-derived on last-socket close only.

05 Reconnect, resume & convergence

At-least-once via replay: the server buffers every dispatch per session for the resume window; the client guards duplicates by sequence. When the session is gone (server restart), a fresh Identify resets the epoch and the client re-hydrates REST state to converge what it missed.

Claim: two convergence mechanisms, one contract — Resume replays exactly the gap; a dead session re-Identifies and the epoch bump drives REST re-hydration so a reload is never required. The soak enforces the zero-loss half; a known open issue is an intermittent post-restart live-delivery gap (1–17 missed by one client, decode clean, persistence intact) found by exactly that enforcement.
